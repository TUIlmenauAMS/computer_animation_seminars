Chapter 02: Three.js

Three.js is a high-level JavaScript library that puts a scene-graph-based API on top of WebGL. Instead of managing shaders, buffer objects, and draw calls by hand — as you did in Chapter 01 — you describe your scene as a tree of objects (meshes, lights, cameras) and Three.js handles the GPU calls beneath the surface.

This chapter builds on everything from Chapter 01. If you understand vertex buffers, shaders, the MVP matrix pipeline, and the animation loop, you are already prepared: Three.js is an abstraction of those exact ideas. By the end of this chapter you will be able to build complete interactive 3D scenes with materials, lighting, shadows, and keyframe animation — and you will understand precisely what Three.js is doing under the hood, because you have already done it yourself in raw WebGL.

1. What is Three.js

Three.js is a JavaScript library for real-time 3D graphics on the web. It wraps the verbose, stateful WebGL API into a clean, object-oriented scene-graph system. You describe a scene — its objects, lights, and cameras — and Three.js renders it through WebGL without you writing a single line of GLSL or manually binding a single buffer.

It was created by Ricardo Cabello (known as mrdoob), with the first commit in April 2010. As of 2024 it is at revision r165+, MIT licensed, and maintained by a large open-source community. With over 100,000 GitHub stars it is the most widely used 3D library on the web.

The Three.js ecosystem

Three.js sits at the base of a broader stack of libraries built on top of it:

  • Three.js core — the renderer, scene graph, geometry, materials, animation system. This is what you will learn in this chapter.
  • React Three Fiber (R3F) — a React renderer for Three.js. Lets you describe a Three.js scene in JSX. Used in production at many studios.
  • Drei — a helper library for R3F with ready-made components (orbit controls, environment maps, text, etc.).
  • Rapier, Cannon.js, Ammo.js — physics engines that integrate with Three.js (covered in Seminar 05).
  • GSAP — a professional animation library for DOM, SVG, and Three.js objects (covered in Seminar 06).

What Three.js does not do

Three.js handles rendering only. It does not include physics simulation, spatial audio, AI behaviour, or networking. These are separate libraries that work alongside Three.js — you will meet several of them in later seminars.

The relationship to raw WebGL

Three.js is a layer on top of WebGL, not a replacement. Every object you create in Three.js — a Mesh, a DirectionalLight, a MeshStandardMaterial — eventually becomes WebGL calls: buffer uploads, shader uniform updates, draw calls. The underlying concepts from Chapter 01 (VBOs, VAOs, shaders, the depth buffer, the MVP matrix) are all still there. Three.js just manages them for you.

Understanding raw WebGL first — as you now do — means you can read Three.js source code, debug unexpected behaviour, write custom ShaderMaterial effects, and understand the performance implications of every API call. That knowledge is the difference between using Three.js and understanding it.

Industry adoption: Three.js is used by Google, NASA, The New York Times, Apple, and hundreds of interactive studios for product configurators, data visualizations, browser games, and immersive web experiences. It is the most likely library you will encounter on the job if you build for the web.

2. Setup and the Rendering Loop

Importing Three.js with an import map

The modern official way to use Three.js is via ES module import maps. An import map tells the browser which URL to fetch when JavaScript code uses a bare module specifier like import * as THREE from 'three'. This is cleaner than the legacy <script src> approach: you get proper ES module syntax, tree-shaking potential, and the ability to import addons (OrbitControls, loaders) from the same CDN package.

<!-- 1. Declare the import map BEFORE any module scripts -->
<script type="importmap">
{
  "imports": {
    "three": "https://cdn.jsdelivr.net/npm/three@0.165.0/build/three.module.js",
    "three/addons/": "https://cdn.jsdelivr.net/npm/three@0.165.0/examples/jsm/"
  }
}
</script>

<!-- 2. Your code as a module script -->
<script type="module">
import * as THREE from 'three';
import { OrbitControls } from 'three/addons/controls/OrbitControls.js';
// Additional addons follow the same pattern:
// import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js';
</script>

Always pin Three.js to an exact version (0.165.0 in this course). Never use latest — Three.js does not maintain backwards compatibility between revisions, and a silent version upgrade can break your code.

The four essential objects

Every Three.js scene needs four things:

  • WebGLRenderer — manages the WebGL context and draws the scene to a canvas.
  • Scene — the root container. All objects (meshes, lights) are added here.
  • Camera — defines the viewpoint. Usually a PerspectiveCamera.
  • Mesh — a visible object: geometry (shape) + material (appearance).

Complete minimal scene

import * as THREE from 'three';
import { OrbitControls } from 'three/addons/controls/OrbitControls.js';

// ── RENDERER ─────────────────────────────────────────────────────────────────
// WebGLRenderer creates a <canvas> element and a WebGL2 context on it.
const renderer = new THREE.WebGLRenderer({ antialias: true });

// setPixelRatio: multiplies the drawing buffer size by the screen's DPR.
// Without this, the canvas looks blurry on retina / HiDPI screens.
renderer.setPixelRatio(window.devicePixelRatio);

// Fill the window. This sets canvas.width/height (the GPU buffer size),
// not CSS size. We keep them in sync on resize (see below).
renderer.setSize(window.innerWidth, window.innerHeight);
document.body.appendChild(renderer.domElement);

// ── SCENE ────────────────────────────────────────────────────────────────────
// THREE.Scene is the root of the scene graph.
// Every visible object and light is added to the scene.
const scene = new THREE.Scene();
scene.background = new THREE.Color(0x0d0f14);  // match the page background

// ── CAMERA ───────────────────────────────────────────────────────────────────
// PerspectiveCamera(fov, aspect, near, far)
// fov: vertical field of view in degrees
// aspect: canvas width / height — must match the renderer size
// near / far: the clipping planes — geometry outside this range is not drawn
const camera = new THREE.PerspectiveCamera(
  60,                                          // fov
  window.innerWidth / window.innerHeight,      // aspect
  0.1,                                         // near (not too small — see Section 7)
  100                                          // far
);
camera.position.set(0, 1.5, 4);  // move the camera back so we can see the scene

// ── LIGHT ────────────────────────────────────────────────────────────────────
// AmbientLight: uniform fill light — no direction, no shadows.
// Without it, the dark side of objects is completely black.
const ambient = new THREE.AmbientLight(0xffffff, 0.4);
scene.add(ambient);

// DirectionalLight: parallel rays from a direction (like the sun).
// The light's position defines the direction from which it comes.
const sun = new THREE.DirectionalLight(0xffffff, 1.2);
sun.position.set(3, 5, 2);
scene.add(sun);

// ── GEOMETRY + MATERIAL ──────────────────────────────────────────────────────
// Mesh = Geometry + Material. They are separate objects and can be reused.
// BoxGeometry(width, height, depth, widthSegments, heightSegments, depthSegments)
const geometry = new THREE.BoxGeometry(1, 1, 1);

// MeshStandardMaterial: PBR (Physically Based Rendering). The default choice.
// It responds correctly to all light types and looks consistent under any lighting.
const material = new THREE.MeshStandardMaterial({
  color: 0x4f9cf9,   // base albedo color
  roughness: 0.4,    // 0 = mirror, 1 = fully diffuse
  metalness: 0.1     // 0 = plastic/dielectric, 1 = metal
});

const cube = new THREE.Mesh(geometry, material);
scene.add(cube);

// ── ORBIT CONTROLS ───────────────────────────────────────────────────────────
// OrbitControls lets the user rotate, pan and zoom the camera with the mouse.
// It listens to pointer events on the renderer's canvas element.
const controls = new OrbitControls(camera, renderer.domElement);
controls.enableDamping = true;     // smooth inertia effect
controls.dampingFactor = 0.05;

// ── RESIZE HANDLER ───────────────────────────────────────────────────────────
// When the window resizes we must update both the renderer size
// and the camera's aspect ratio, then call updateProjectionMatrix().
window.addEventListener('resize', () => {
  camera.aspect = window.innerWidth / window.innerHeight;
  camera.updateProjectionMatrix();
  renderer.setSize(window.innerWidth, window.innerHeight);
});

// ── ANIMATION LOOP ───────────────────────────────────────────────────────────
// THREE.Clock gives us accurate delta time (time since last frame in seconds).
// Always use delta time — never animate by a fixed amount per frame,
// because frame rate varies between devices.
const clock = new THREE.Clock();

// renderer.setAnimationLoop is Three.js's built-in loop helper.
// Internally it calls requestAnimationFrame for you.
renderer.setAnimationLoop(() => {
  const delta = clock.getDelta();      // seconds since last frame

  // ANIMATION CONCEPT: time-based rotation.
  // Multiplying by delta makes the rotation speed frame-rate-independent.
  // On a 30fps device and a 120fps device the cube rotates at the same angular speed.
  cube.rotation.y += 0.6 * delta;
  cube.rotation.x += 0.2 * delta;

  controls.update();                   // required when enableDamping is true
  renderer.render(scene, camera);      // draw the scene from the camera's viewpoint
});

devicePixelRatio: On a MacBook with a Retina screen, window.devicePixelRatio is 2. Without setPixelRatio(window.devicePixelRatio), Three.js renders at the CSS pixel resolution and the browser stretches the image to fill the physical pixels — the result looks blurry. With it, the GPU draws at full physical resolution. On most phones the DPR is 2 or 3. For performance-critical applications you can cap it: renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2)).

3. The Scene Graph

A scene graph is a tree of objects, each with its own local coordinate system. When you place an object in the scene you can set its position, rotation, and scale relative to its parent. The world transform of any object is the product of all the transforms from the root down to that object.

In Three.js, the base class for every object in the scene graph is THREE.Object3D. Meshes, lights, cameras, and groups all inherit from it and all have a local transform: .position (Vector3), .rotation (Euler), and .scale (Vector3).

Parent–child relationships

// parent.add(child) attaches child to parent's local coordinate system.
// Moving the parent moves the child with it.
const parent = new THREE.Group();
parent.position.set(2, 0, 0);    // parent is 2 units to the right

const child = new THREE.Mesh(geometry, material);
child.position.set(0, 1, 0);    // child is 1 unit up FROM THE PARENT

parent.add(child);
scene.add(parent);
// child's world position = (2, 1, 0) — the two offsets stack

How transforms propagate

Three.js computes each object's world matrix automatically every frame by multiplying the parent's world matrix by the child's local matrix:

worldMatrix(child) = worldMatrix(parent) × localMatrix(child)

You never call this yourself for standard scenes — Three.js handles the matrix update traversal during renderer.render(). If you need the world matrix early (before render), call object.updateWorldMatrix(true, true).

Quaternion vs Euler rotation

object.rotation is an Euler — three angles (x, y, z) applied in a fixed order. Euler angles are intuitive but suffer from gimbal lock: when two rotation axes align, one degree of freedom is lost and you can no longer rotate in all directions. Internally, Three.js represents rotation as a quaternion (object.quaternion), a 4-component value that never gimbal-locks and interpolates cleanly with slerp (spherical linear interpolation). For most animation work you can use Euler angles without issue; for smooth rotation interpolation (as in the QuaternionKeyframeTrack discussed in Section 10), the quaternion path is the correct one.

Traversal and lookup

// Visit every object in the scene graph depth-first:
scene.traverse((object) => {
  if (object.isMesh) {
    console.log(object.name, object.position);
  }
});

// Find a specific object by name (set with object.name = 'myBox'):
const box = scene.getObjectByName('myBox');

// Get the world position of any object (avoids computing it manually):
const worldPos = new THREE.Vector3();
object.getWorldPosition(worldPos);

The scene graph is universal: Unity's Transform hierarchy, Unreal's Actor/Component system, Blender's object parenting, and every major 3D tool use the same data structure — a tree of local transforms. A character rig is a scene graph (the hip is the root, limbs are children). A solar system is a scene graph (the Sun is the root, planets are children, moons are grandchildren). Learning it in Three.js transfers directly everywhere else.

4. Geometry

In Three.js, all geometry is represented as a BufferGeometry. This is a direct mapping of the GPU buffer model from Chapter 01: each vertex attribute (position, normal, UV, index) is stored as a typed JavaScript array and uploaded to the GPU as a VBO or EBO. A BufferGeometry is essentially the Three.js wrapper around what you built manually with gl.createBuffer() and gl.vertexAttribPointer().

Key attributes

AttributeTypeDescription
positionFloat32Array (xyz per vertex)Vertex positions in local space
normalFloat32Array (xyz per vertex)Surface normals for lighting. Same as the normals uploaded to the GPU in Chapter 01.
uvFloat32Array (uv per vertex)Texture coordinates. Built-in geometries include UVs; custom geometry needs them added manually.
indexUint16Array or Uint32ArrayIndex buffer — reuses vertices, exactly as the EBO in Chapter 01.

Built-in geometries

Three.js ships a library of parametric geometries so you rarely need to build geometry by hand:

ClassParametersTypical use
BoxGeometrywidth, height, depth, segments×3Cube, wall, crate
SphereGeometryradius, widthSegs, heightSegsBall, planet, head
PlaneGeometrywidth, height, segments×2Ground plane, quad
CylinderGeometryradiusTop, radiusBottom, height, segsPillar, tree trunk
CapsuleGeometryradius, length, capSegs, radialSegsCharacter placeholder, rigid body
TorusGeometryradius, tube, radialSegs, tubularSegsRing, donut
TorusKnotGeometryradius, tube, p, qDecorative organic shape

The segments parameter controls tessellation: more segments make a smoother curved surface but increase vertex count and draw time. A SphereGeometry(1, 8, 6) looks like a faceted gem; SphereGeometry(1, 64, 48) looks smooth. For most demos, 32×24 is a good balance.

Custom geometry

When built-in shapes are not enough, you can create a BufferGeometry from scratch — this is exactly the process you followed in Chapter 01:

const geo = new THREE.BufferGeometry();

// A flat quad (two triangles) in the XZ plane:
const positions = new Float32Array([
  -1, 0,  1,   // vertex 0
   1, 0,  1,   // vertex 1
   1, 0, -1,   // vertex 2
  -1, 0, -1    // vertex 3
]);
geo.setAttribute('position', new THREE.BufferAttribute(positions, 3));

const indices = new Uint16Array([0, 1, 2,  0, 2, 3]);
geo.setIndex(new THREE.BufferAttribute(indices, 1));

// Compute normals automatically from position data:
geo.computeVertexNormals();  // required for lighting to work on custom geometry

Geometry reuse and disposal

A geometry object is a GPU resource. If you need the same shape for many meshes, share the geometry object — do not create a new one per mesh. When you remove an object from the scene permanently, call geometry.dispose() to free the GPU memory. The same applies to materials and textures.

Mesh = Geometry + Material. The geometry defines the shape — the positions, normals, and UVs. The material defines the appearance — the shader, the color, and the texture maps. They are independent objects and can be mixed and matched freely. One geometry can be used with many different materials; one material can be shared across many meshes.

5. Materials

A material defines how a surface looks. Three.js provides a stack of materials ranging from the extremely cheap and simple to the physically accurate:

MaterialLightingCostUse case

MeshLambertMaterialDiffuse only (Lambertian)LowLarge numbers of low-importance objects; foliage
MeshPhongMaterialDiffuse + specular (Phong model)MediumLegacy projects; shiny plastic look; not physically correct
MeshStandardMaterialFull PBR (metalness/roughness)Medium–HighThe default choice for any realistic surface
MeshPhysicalMaterialPBR + clearcoat, sheen, transmissionHighGlass, car paint, fabric, skin

ShaderMaterialCustom GLSL (you write the shader)DependsAny effect not achievable with the above; connects to Chapter 01

PBR — Physically Based Rendering

MeshStandardMaterial implements the metalness / roughness PBR model. Two parameters control the entire material response:

  • metalness (0–1): 0 = dielectric (plastic, wood, skin), 1 = metal (iron, gold, chrome). Metals reflect light differently from dielectrics — their specular color comes from the base color, not from white highlights.
  • roughness (0–1): 0 = perfectly smooth mirror surface, 1 = fully diffuse (no specular at all). Intermediate values produce realistic brushed or matte surfaces.

Real-world reference values for common surfaces:

Materialmetalnessroughness
Chrome / polished metal1.00.05–0.1
Brushed aluminum1.00.4–0.6
Gold1.00.15–0.3
Matte plastic0.00.8–1.0
Glossy plastic0.00.1–0.3
Wood0.00.7–0.9
Wet concrete0.00.4–0.6

Shared material properties

const mat = new THREE.MeshStandardMaterial({
  color: 0xffffff,           // base albedo color (Color, hex number, or string)
  emissive: 0x000000,        // self-illumination color — not affected by lights
  roughness: 0.5,
  metalness: 0.0,
  wireframe: false,          // render as wireframe instead of solid
  side: THREE.FrontSide      // THREE.FrontSide | THREE.BackSide | THREE.DoubleSide
});

// When you no longer need the material, free the GPU program:
mat.dispose();

PBR everywhere: Physically Based Rendering was adopted by every major real-time engine around 2013–2015 — Unreal Engine 4, Unity 5, and Frostbite all switched to metalness/roughness PBR in that period. MeshStandardMaterial implements the same model. The parameters you set in Three.js map directly to the PBR inputs in Unreal's Material Editor, Unity's Standard Shader, and Blender's Principled BSDF node.

6. Lighting

Light is required for MeshStandardMaterial, MeshLambertMaterial, and MeshPhongMaterial to show any shading. Only MeshBasicMaterial ignores lights. Three.js supports several light types, each with a different physical model and performance cost.

Light types

LightModelShadowsParameters
AmbientLightUniform fill from all directionsNocolor, intensity
DirectionalLightParallel rays — like the sunYescolor, intensity, position (defines direction)
PointLightRadiates in all directions from a pointYes (6 passes)color, intensity, distance, decay
SpotLightCone of light from a point toward a targetYescolor, intensity, distance, angle, penumbra, decay
HemisphereLightSky color from above, ground color belowNoskyColor, groundColor, intensity
RectAreaLightRectangular area emitter — soft, realisticNocolor, intensity, width, height

Light helpers

Lights are invisible objects. Helpers draw a visual representation of the light's position, direction, and frustum — essential for debugging:

const sun = new THREE.DirectionalLight(0xfff5e0, 1.5);
sun.position.set(5, 8, 3);
scene.add(sun);

// DirectionalLightHelper draws an arrow in the light's direction:
const helper = new THREE.DirectionalLightHelper(sun, 1);
scene.add(helper);

// Update the helper when the light moves:
helper.update();

Physically correct light units

Since Three.js r155, the renderer uses physically correct light units by default (renderer.useLegacyLights = false is the new default). Point and Spot lights use candela; Directional lights use lux. If you are upgrading a scene from an older Three.js version and lights appear very bright or very dim, this is why. For this course, tune intensity values empirically — typical values are 0.5–2.0 for directional lights and 50–200 for point lights at close range.

Typical production lighting setup

// The standard outdoor scene setup:
// HemisphereLight provides sky/ground ambient fill (no shadows, cheap).
// DirectionalLight provides the sun (shadows, directional shading).
const hemi = new THREE.HemisphereLight(0xb1e1ff, 0x5a3e2b, 0.6); // sky, ground, intensity
scene.add(hemi);

const sun = new THREE.DirectionalLight(0xfff5e0, 1.5);
sun.position.set(5, 10, 5);
scene.add(sun);

Common production setup: A HemisphereLight (sky/ground ambient) plus one DirectionalLight (sun) is the standard starting point for outdoor Three.js scenes. This is the setup used in Three.js Journey and most Three.js production work. For indoor scenes, substitute a low-intensity AmbientLight for the hemisphere, and one or two PointLights for practical lamps.

7. Cameras

PerspectiveCamera

The standard camera for 3D scenes. It matches human vision — objects farther away appear smaller, parallel lines converge. Defined by four parameters:

// PerspectiveCamera(fov, aspect, near, far)
const camera = new THREE.PerspectiveCamera(
  60,                                // fov — vertical field of view in degrees
  window.innerWidth / window.innerHeight,  // aspect — must match renderer size
  0.1,                               // near clip plane
  1000                               // far clip plane
);
  • fov: vertical field of view in degrees. Typical range: 45° (natural, telephoto) to 75° (wide, game-style). Higher FOV looks more dramatic; lower FOV looks more compressed.
  • aspect: canvas width divided by height. Must be updated when the window resizes.
  • near: the near clip plane. Geometry closer than this distance is not drawn. Keep it as large as possible — a very small near value (like 0.0001) degrades depth buffer precision and causes Z-fighting (flickering surfaces at similar depths).
  • far: the far clip plane. Geometry beyond this distance is not drawn. Keep it as small as possible for the same depth precision reason.

This is the same perspective projection matrix you built manually with mat4.perspective in Chapter 01. camera.position and camera.lookAt() produce the same view matrix you built with mat4.lookAt.

OrthographicCamera

An orthographic camera renders with no perspective distortion — objects appear the same size regardless of distance. Used for 2D UIs, technical/architectural views, and isometric game cameras:

// OrthographicCamera(left, right, top, bottom, near, far)
const aspect = window.innerWidth / window.innerHeight;
const camera = new THREE.OrthographicCamera(
  -aspect, aspect,  // left, right
  1, -1,            // top, bottom
  0.1, 100          // near, far
);

Resize handling

Whenever the window resizes you must update the camera and renderer together:

window.addEventListener('resize', () => {
  // Update renderer drawing buffer size:
  renderer.setSize(window.innerWidth, window.innerHeight);

  // Update camera aspect ratio and recompute projection matrix:
  camera.aspect = window.innerWidth / window.innerHeight;
  camera.updateProjectionMatrix();  // required after any change to fov, aspect, near, far
});

FOV and lens equivalence: A FOV of 50°–60° roughly matches a 50mm lens on a 35mm camera — the classic 'natural' look with minimal distortion. Wide FOV (90°+) gives peripheral vision and is common in first-person games. Narrow FOV (30°–40°) produces a telephoto, compressed-perspective look often used in cinematic shots. In Three.js, fov is the vertical field of view; horizontal FOV is derived automatically from the aspect ratio.

8. Controls

OrbitControls is a Three.js addon that gives the user mouse and touch control over the camera: orbit (left-drag or one-finger), pan (right-drag or two-finger translate), and zoom (scroll wheel or pinch). It is not part of the Three.js core — it lives in the examples and is imported from three/addons/.

Basic setup

import { OrbitControls } from 'three/addons/controls/OrbitControls.js';

const controls = new OrbitControls(camera, renderer.domElement);

// Damping: adds inertia so camera movement feels smooth.
// When enabled, controls.update() must be called every frame.
controls.enableDamping = true;
controls.dampingFactor = 0.05;   // lower = more inertia

// The point the camera orbits around:
controls.target.set(0, 0.5, 0); // orbit around a point slightly above the origin
controls.update();               // apply target change immediately

// Zoom limits:
controls.minDistance = 1;
controls.maxDistance = 50;

// Elevation limits (prevent camera from going underground):
controls.minPolarAngle = 0;             // 0 = directly above the target
controls.maxPolarAngle = Math.PI / 2;   // PI/2 = horizon level

// Auto-rotate when the user is not interacting:
controls.autoRotate = true;
controls.autoRotateSpeed = 1.0;  // rpm

In the animation loop

renderer.setAnimationLoop(() => {
  controls.update();  // must be called every frame when damping or autoRotate is on
  renderer.render(scene, camera);
});

How OrbitControls works

OrbitControls listens to pointer events (pointerdown, pointermove, pointerup) on the renderer's canvas element. It converts the mouse delta into changes to spherical coordinates (azimuth angle, elevation angle, radius) around the target point, then converts those back to Cartesian coordinates and sets camera.position. This is exactly the orbit math from the camera demo in Chapter 01 — OrbitControls just wraps it in a reusable, production-hardened class.

When you no longer need the controls (e.g. when destroying the renderer), call controls.dispose() to remove all event listeners.

OrbitControls implements the Chapter 01 camera demo: The spherical coordinate orbit (azimuth, elevation, radius) from Seminar 01's 01_ca_camera.html is exactly what OrbitControls does internally, with the addition of pan (truck + pedestal) and pinch zoom. Reading the OrbitControls source is an excellent exercise — it is well-commented and uses only the math you already know.

9. Shadows

Three.js renders shadows using a classic shadow map technique: the scene is first rendered from the light's point of view into a depth texture (the shadow map). During the main render, each fragment checks whether its position — when projected into the light's view — is behind the depth stored in the shadow map. If so, the fragment is in shadow.

Enabling shadows — five steps

// Step 1: Enable shadow rendering on the renderer.
renderer.shadowMap.enabled = true;

// Step 2: Choose the shadow map filter type.
// PCFSoftShadowMap: soft edges via Percentage Closer Filtering — the standard choice.
renderer.shadowMap.type = THREE.PCFSoftShadowMap;

// Step 3: Enable shadow casting on the light.
// Only DirectionalLight, SpotLight, and PointLight support shadows.
const sun = new THREE.DirectionalLight(0xffffff, 1.5);
sun.castShadow = true;

// Step 4: Set shadow map resolution (default: 512×512).
// Higher = sharper shadows, more GPU memory.
sun.shadow.mapSize.width  = 2048;
sun.shadow.mapSize.height = 2048;

// Step 5: Mark which meshes cast and receive shadows.
cube.castShadow = true;       // this mesh casts a shadow onto other objects
ground.receiveShadow = true;  // this mesh shows shadows from other objects
// Note: objects can be both casters and receivers.

The shadow camera

Every shadow-casting light has an internal camera (light.shadow.camera) that defines the frustum the shadow map covers. For a DirectionalLight, this is an OrthographicCamera — its left, right, top, and bottom extents must be sized to tightly enclose your scene. If the frustum is too small, shadows are clipped at the edges; if it is too large, the shadow map resolution is wasted over empty space.

// Size the shadow camera frustum to fit a 10×10m scene:
sun.shadow.camera.left   = -10;
sun.shadow.camera.right  =  10;
sun.shadow.camera.top    =  10;
sun.shadow.camera.bottom = -10;
sun.shadow.camera.near   = 0.5;
sun.shadow.camera.far    = 50;

// Visualize the shadow camera frustum for debugging:
const shadowHelper = new THREE.CameraHelper(sun.shadow.camera);
scene.add(shadowHelper);

Shadow maps are universal: This technique is used in Unity, Unreal Engine, Godot, and every major real-time renderer. The tradeoffs — resolution vs performance, shadow acne vs bias, cascade splits for large outdoor scenes — are identical across all engines. Mastering shadow maps in Three.js gives you the same mental model you will use in any engine.

10. The Animation System

Three.js has a complete, production-grade keyframe animation system. Its architecture is the same as what you built manually in Chapter 01 — keyframe arrays, interpolation, a time value that advances each frame — but wrapped in a reusable API that handles multiple properties, multiple clips, and blending between clips simultaneously.

The four core objects

Understanding the relationship between these four objects is the key to the animation system:

ObjectWhat it isAnalogy
KeyframeTrackA single property animated over time — times array + values array + interpolation modeOne row in a spreadsheet — one column per keyframe
AnimationClipA named collection of tracks with a total durationOne "take" — e.g. "idle", "walk", "jump"
AnimationMixerThe playback engine attached to a root object; advances internal time each frameThe playback head — moves through all active clips
AnimationActionControls playback of one clip: play, pause, loop mode, time scale, blend weightA track in a DAW — can be muted, soloed, faded

KeyframeTrack subclasses

// VectorKeyframeTrack — for position and scale (Vector3 values):
// Constructor: (propertyPath, times[], values[], interpolation)
// propertyPath: '.position' animates object.position.x/y/z
const posTrack = new THREE.VectorKeyframeTrack(
  '.position',
  [0,    1,    2,    3   ],  // times in seconds
  [0,0,0, 2,0,0, 0,0,-2, 0,0,0],  // values: x,y,z at each time (flat array)
  THREE.InterpolateLinear         // interpolation mode
);

// QuaternionKeyframeTrack — for rotation (Quaternion values, uses slerp):
// ANIMATION CONCEPT: quaternion slerp produces constant angular speed.
// Regular lerp on quaternions produces variable speed due to the unit sphere mapping.
const rotTrack = new THREE.QuaternionKeyframeTrack(
  '.quaternion',
  [0,     2    ],
  [0,0,0,1, 0,1,0,0]  // identity quaternion → 180° Y rotation (x,y,z,w)
);

// NumberKeyframeTrack — for a single numeric property:
const scaleTrack = new THREE.VectorKeyframeTrack(
  '.scale',
  [0,   0.5,  1   ],
  [1,1,1, 2,2,2, 1,1,1]  // pulse: grow and shrink
);

Interpolation modes

ModeBehaviourUse case
THREE.InterpolateLinearStraight-line lerp between keyframesMechanical motion, simple loops
THREE.InterpolateSmoothCatmullRom spline — smooth, overshoots slightlyOrganic character motion — the same curve type as Blender's Auto Bezier
THREE.InterpolateDiscreteStep / hold — jumps instantly at each keyframeFrame-by-frame animation, visibility on/off

Building and playing a clip

// Combine tracks into a named clip:
const clip = new THREE.AnimationClip(
  'bounce',        // name
  3,               // duration in seconds (-1 = auto from tracks)
  [posTrack, rotTrack, scaleTrack]
);

// Create a mixer attached to the object you want to animate:
const mixer = new THREE.AnimationMixer(sphere);

// Get an action for the clip:
const action = mixer.clipAction(clip);

// Configure playback:
action.loop = THREE.LoopRepeat;   // LoopRepeat | LoopOnce | LoopPingPong
action.timeScale = 1.0;          // 1 = normal, 2 = double speed, -1 = reverse

// Start playback:
action.play();

Updating the mixer in the animation loop

const clock = new THREE.Clock();

renderer.setAnimationLoop(() => {
  // ANIMATION CONCEPT: mixer.update(delta) advances the mixer's internal time
  // by delta seconds. The mixer then evaluates all active tracks at the new time
  // and applies the interpolated values to the animated object.
  // Passing delta (not absolute time) means pausing the mixer is trivial —
  // just stop calling update(), or call it with 0.
  const delta = clock.getDelta();
  mixer.update(delta);

  controls.update();
  renderer.render(scene, camera);
});

Clip blending

Multiple AnimationActions can play simultaneously on the same mixer. Each action has a weight (0 = silent, 1 = full influence). By animating the weights, you blend between clips — the core technique behind every character animation system:

// Cross-fade from idle to walk over 0.5 seconds:
idleAction.crossFadeTo(walkAction, 0.5, true);

This pattern — tracks → clips → mixer → weighted actions — is used in glTF 2.0 animations (Seminar 04), Unity's Animator Controller, and Unreal's Animation Blueprint. Learning it in Three.js is learning a transferable architectural pattern.

The animation system is universal: Three.js KeyframeTrack is the same concept as the manual keyframe arrays in 01_ca_keyframes.html — Three.js wraps the same lerp math into a reusable system. QuaternionKeyframeTrack uses slerp (spherical linear interpolation) instead of lerp for rotation — the quaternion equivalent of lerp, producing constant angular speed. THREE.InterpolateSmooth uses a CatmullRom spline — the same curve type as Blender's and Maya's graph editor "Auto" handles.

11. Textures and Environment Maps

Loading textures

A texture in Three.js is a Texture object wrapping a GPU texture. The TextureLoader loads an image from a URL, uploads it to the GPU, and returns the texture:

const loader = new THREE.TextureLoader();

// Load a texture asynchronously. onLoad fires when the image is ready.
const albedo = loader.load(
  'https://example.com/textures/brick_albedo.jpg',
  (texture) => { console.log('loaded'); },   // onLoad
  undefined,                                  // onProgress
  (err) => { console.error(err); }           // onError
);

// IMPORTANT: set colorSpace for color/albedo textures.
// Normal, roughness, and metalness maps are NOT sRGB — don't set this for them.
albedo.colorSpace = THREE.SRGBColorSpace;

// Assign to material channel:
const mat = new THREE.MeshStandardMaterial({
  map:          albedo,     // albedo / base color
  normalMap:    normalTex,  // surface detail normals (TBN space)
  roughnessMap: roughTex,   // per-pixel roughness (R channel)
  metalnessMap: metalTex,   // per-pixel metalness (R channel)
  aoMap:        aoTex,      // ambient occlusion (R channel)
});

UV mapping

UV coordinates map a 2D texture to a 3D surface. Every vertex has a U (horizontal) and V (vertical) coordinate in 0–1 range. Three.js's built-in geometries all include UVs. For custom geometry you must add them manually as a uv attribute (Float32Array, 2 components per vertex).

Texture tiling (repeating the texture across a large surface) is controlled by texture.repeat and texture.wrapS/.wrapT:

albedo.wrapS = THREE.RepeatWrapping;   // repeat horizontally
albedo.wrapT = THREE.RepeatWrapping;   // repeat vertically
albedo.repeat.set(4, 4);              // tile 4 times in each direction

Mipmaps

Three.js generates mipmaps automatically for power-of-two textures (texture.generateMipmaps = true by default). Mipmaps are pre-downscaled versions of the texture (half width, quarter size, etc.) stored alongside the full-resolution image. The GPU picks the mip level that best matches the on-screen texel density, which eliminates aliasing on distant surfaces and improves cache coherence — a measurable performance improvement on large scenes.

Environment maps for PBR

A scene environment map is the single biggest quality improvement for PBR materials. It is an HDR panorama of a real-world environment that acts as ambient light and reflection source. Setting scene.environment applies it to all MeshStandardMaterial objects in the scene:

import { RGBELoader } from 'three/addons/loaders/RGBELoader.js';

const pmremGen = new THREE.PMREMGenerator(renderer);
pmremGen.compileEquirectangularShader();

// RGBELoader loads .hdr equirectangular panoramas:
new RGBELoader().load('https://dl.polyhaven.org/file/ph-assets/HDRIs/hdr/1k/studio_small_08_1k.hdr',
  (hdr) => {
    // PMREMGenerator pre-filters the HDR for PBR use — required for correct reflections:
    const envMap = pmremGen.fromEquirectangular(hdr).texture;
    scene.environment = envMap;     // all PBR materials use this for lighting and reflections
    scene.background  = envMap;     // optional: use as the visible sky
    hdr.dispose();
    pmremGen.dispose();
  }
);

Environment maps are the biggest single upgrade: A well-chosen HDR environment makes MeshStandardMaterial look photorealistic with zero extra point or directional lights. Free, high-quality HDRIs are available at Poly Haven under a CC0 license — they can be loaded directly from their CDN in demos.

12. Performance and Best Practices

Real-time animation must sustain 60 frames per second — a budget of 16.6 ms per frame. Three.js gives you the tools to diagnose and fix performance problems, but the responsibility for efficient scene design is yours.

Draw calls

A draw call is a command from the CPU to the GPU to render a set of triangles. Each Mesh.render() produces one draw call. Draw calls are expensive not because of what they draw, but because of the overhead of the CPU–GPU communication per call. A scene with 1,000 draw calls of 10 triangles each is much slower than one draw call of 10,000 triangles.

Monitor draw calls with renderer.info:

// Print live stats (call inside the render loop):
console.log(
  `Draw calls: ${renderer.info.render.calls}  |  ` +
  `Triangles:  ${renderer.info.render.triangles}  |  ` +
  `Geometries: ${renderer.info.memory.geometries}  |  ` +
  `Textures:   ${renderer.info.memory.textures}`
);

Instanced rendering

InstancedMesh renders thousands of identical objects in a single draw call. Each instance has its own transform matrix (and optionally its own color), but they all share one geometry and one material:

// InstancedMesh(geometry, material, count)
// Renders 1000 boxes in ONE draw call:
const count = 1000;
const iMesh = new THREE.InstancedMesh(boxGeo, boxMat, count);
scene.add(iMesh);

const matrix = new THREE.Matrix4();
for (let i = 0; i < count; i++) {
  // Set each instance's world transform:
  matrix.setPosition(
    (Math.random() - 0.5) * 50,
    Math.random() * 10,
    (Math.random() - 0.5) * 50
  );
  iMesh.setMatrixAt(i, matrix);
}
iMesh.instanceMatrix.needsUpdate = true;  // upload to GPU

Geometry and material reuse

Never create a new geometry or material inside the render loop. Create them once, reuse them across as many meshes as possible. One BoxGeometry(1,1,1) instance can be shared by a thousand meshes with no extra GPU memory.

Disposal

When you remove objects from the scene permanently, free the GPU resources they held. Forgetting to dispose is the most common cause of memory leaks in Three.js applications:

// Remove and dispose a mesh:
scene.remove(mesh);
mesh.geometry.dispose();
mesh.material.dispose();
if (mesh.material.map) mesh.material.map.dispose();

// Full renderer cleanup (when destroying the entire canvas):
renderer.dispose();

Shadow performance

Each shadow-casting light requires a full extra render pass of the scene into the shadow map. Two shadow-casting lights = three render passes total (two shadow passes + one main pass). Limit shadow-casting lights to the minimum needed — typically one directional (sun) is sufficient. For static geometry, consider baking shadows to textures instead.

renderer.info is your first diagnostic tool. Add a live stats line to every Three.js demo you build — displaying draw calls, triangle counts, and memory usage. A sudden spike in draw calls after adding an object tells you immediately that instancing or merging is needed. The Three.js team uses this internally, and so do professional studios.
