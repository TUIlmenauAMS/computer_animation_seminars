Chapter 03: PySide6 & Python Animation

So far in this course every interactive demo has run in a browser: a canvas element, WebGL, JavaScript. This chapter switches to the desktop. You will build GUI applications with PySide6 — the same Qt framework that powers Maya, Nuke, Houdini, and Katana — and connect them to a live OpenGL rendering context using PyOpenGL. The animation math (interpolation, easing, matrix transforms) is handled by NumPy, and the whole project is managed with uv, the modern Python package manager.

The animation concepts do not change. A timeline widget driven by a QTimer is the same idea as requestAnimationFrame. A QPainter Bézier curve is the same cubic polynomial as the CSS cubic-bezier() you visualised in Chapter 01. An OpenGL viewport inside a Qt window uses the same GPU pipeline — VAO, VBO, GLSL shaders, MVP matrix — as Chapter 01's raw WebGL and Chapter 02's Three.js. The language and the API surface are different; the concepts are identical.

1. Why Python for Animation Tooling

The two-language world of production animation

Every major animation and VFX tool is built on two languages working together. The engine layer — the renderer, the physics solver, the simulation core — is written in C++ and GLSL because performance is non-negotiable: a single frame of a Hollywood feature can involve billions of ray intersections, and that work must run at maximum CPU and GPU throughput. But above the engine sits a vast second layer: the pipeline. This is where assets flow between departments, where riggers automate character setups, where TDs write export scripts and batch processing tools, and where artists build custom UIs for specialised workflows. That second layer is almost universally Python.

  • Autodesk Maya — full Python API (maya.cmds, maya.api) for scripting and plugin development. Every production studio has thousands of lines of Maya Python.
  • SideFX Houdini — Python SOPs, TOPs, PDG networks. Houdini's entire procedural pipeline is scriptable in Python.
  • Foundry Nuke — Python API for compositing node graphs, custom gizmos, batch rendering pipelines.
  • Blender — bpy, the Blender Python API. Every Blender add-on is a Python module.
  • Pixar's USD — the Universal Scene Description format has a full Python API used across the entire pipeline at Pixar, ILM, Disney, and every VFX house that has adopted USD.
  • Custom pipeline tools — asset management, shot tracking, render farm submission, review tools. At ILM, Pixar, DNEG, Framestore: all Python.

PySide6 vs PyQt6

Both PySide6 and PyQt6 are Python bindings for the same Qt 6 C++ framework. The code is nearly identical — the difference is licensing and who maintains the binding.

PropertyPySide6PyQt6
Maintained byThe Qt Company (official)Riverbank Computing (third party)

The LGPL licence means you can link PySide6 into a closed-source commercial application without paying anything, as long as you allow end users to relink against a modified PySide6 (which is satisfied by using the standard PyPI package). GPL would require your entire application to be open-source. This is why every VFX studio uses PySide6.

Qt: the UI toolkit of the VFX industry

Qt is not just a widget library — it is a complete application framework covering windowing, 2D and 3D graphics, networking, databases, multithreading, XML/JSON, and much more. Qt's QWidget system is the UI layer of Maya, Nuke, Houdini, and Katana. When you write a PySide6 widget in this course you are writing in the same framework those applications use for their panels, parameter sliders, timeline scrubbers, and viewport controls.

Industry shortcut: Maya, Nuke, Houdini, and Katana all expose PySide2 or PySide6 as their embedded Python UI toolkit. A PySide6 widget you write for this course will run inside Maya with minimal changes — just swap the import and adjust any Qt 6 API differences to Qt 5. Learning PySide6 now means you can ship custom tools inside real production applications the day you start a studio job.

2. Project Setup with uv

What is uv?

uv is a fast, modern Python package manager and project tool built by Astral, the same team behind the Ruff linter. It replaces pip, venv, pip-tools, and partially replaces pyenv with a single, consistent tool. uv resolves and installs packages 10–100× faster than pip because it is written in Rust and uses a parallel resolver.

In this course we use uv because it is rapidly becoming the industry standard for Python tooling (2024–2025), it produces lockfiles that guarantee reproducible environments, and it makes the professional practice of pyproject.toml-based projects accessible to students from day one.

What uv creates

After running uv sync you will find four new items in the seminar folder:

  • uv.lock — the lockfile. Every direct and transitive dependency pinned to an exact version and cryptographic hash. Commit this file. It is what guarantees that uv sync gives every student and every CI machine an identical environment — no "works on my machine" drift. This is analogous to package-lock.json in Node.js or Cargo.lock in Rust.
  • .venv/ — the virtual environment: a self-contained Python interpreter plus all installed packages. Never commit this. Add .venv to .gitignore. It is fully reproducible from uv.lock in a few seconds with uv sync.
  • .python-version — an optional one-line file containing 3.12, created by uv init --python 3.12. Tells uv, Ruff, and other tools which Python version to use in this directory.
  • pyproject.toml — already exists; uv may update it when you run uv add.

Reproducibility: The uv.lock file is the single source of truth for the environment. Anyone who clones the repo and runs uv sync gets an identical environment — same package versions, same hashes, same result. On a fast network with a warm cache, uv sync takes under 10 seconds. This is how professional Python projects are managed.

Flat project layout

The seminar folder uses a flat layout: all .py files live directly in seminar_03/, not in a src/ subdirectory. This is the correct layout for a collection of runnable scripts (like pipeline tools or standalone demos) as opposed to an installable package. The src/ layout is used when you want to pip install your own code into another environment; here, students run the files directly with uv run python.

3. PySide6 Architecture

The Qt object model: QObject and parent–child ownership

Every PySide6 class that does something meaningful — widgets, timers, layout managers, file dialogs — inherits from QObject. The key property of QObject is parent–child ownership: when you create a widget with a parent, the parent takes ownership of the child. When the parent is destroyed, Qt automatically destroys all its children. This means you almost never call del or manage widget lifetimes manually — you just set the parent correctly and Qt handles the rest.

from PySide6.QtWidgets import QApplication, QMainWindow, QWidget, QLabel

# Parent ownership: label is owned by central_widget.
# When central_widget is destroyed, label is destroyed too.
central_widget = QWidget()           # parent: None (will be reparented by setCentralWidget)
label = QLabel("Hello", central_widget)  # parent: central_widget

QApplication: the event loop entry point

QApplication is the heart of every Qt application. It initialises Qt internals, sets up the platform plugin (the layer that talks to the OS window manager), and owns the event loop — the main loop that processes user input, timer events, and repaint requests. Every PySide6 program follows the same pattern:

import sys
from PySide6.QtWidgets import QApplication

# QApplication MUST be created before any QWidget.
# sys.argv is passed so Qt can process its own command-line flags
# (e.g. -style, -platform) before your code runs.
app = QApplication(sys.argv)

# ... create widgets here ...

# app.exec() starts the event loop. It blocks here until the last window closes.
# sys.exit() forwards Qt's exit code to the OS.
# Omitting sys.exit() works but is technically incorrect — use it always.
sys.exit(app.exec())

Animation concept — the event loop: app.exec() runs Qt's event loop — the same concept as the browser's event loop that drives requestAnimationFrame. Neither loop runs your code directly; both fire callbacks (slots / rAF callbacks) in response to events: user input, timer expiry, repaint requests. Understanding the event loop is the foundation of every GUI and animation system.

Layouts: the right way to arrange widgets

Never hardcode pixel positions for widgets. Instead, add widgets to a layout, and Qt computes the geometry automatically — including correct behaviour on resize, on different screen DPIs, and on different OS font sizes.

from PySide6.QtWidgets import (
    QWidget, QVBoxLayout, QHBoxLayout, QLabel, QPushButton
)

container = QWidget()

# QVBoxLayout stacks widgets top to bottom.
vbox = QVBoxLayout(container)   # passing parent sets container's layout directly

title = QLabel("Computeranimation")
btn   = QPushButton("Click me")

vbox.addWidget(title)
vbox.addWidget(btn)

# Spacing and margins
vbox.setSpacing(12)                       # pixels between widgets
vbox.setContentsMargins(16, 16, 16, 16)   # left, top, right, bottom

# addStretch() inserts an expanding spacer — pushes everything above it up
# and everything below it down, like CSS flex-grow: 1.
vbox.addStretch()

# ── Nested layouts ───────────────────────────────────────────────────────────
# Layouts can be nested. A QHBoxLayout inside a QVBoxLayout is common.
hbox = QHBoxLayout()
hbox.addWidget(QPushButton("Left"))
hbox.addWidget(QPushButton("Right"))
hbox.addStretch()       # pushes both buttons to the left

vbox.addLayout(hbox)    # nest the row inside the column

4. Signals and Slots

The observer pattern

The observer pattern is one of the most important patterns in software engineering: an object (the subject) maintains a list of dependents (the observers) and notifies them automatically when its state changes. You do not need the subject to know anything about who is observing it — the coupling is loose and one-directional. This is how professional animation tools connect their components: move a rig control and every downstream element (IK solver, blend shape driver, secondary animation) updates automatically, without the control needing to know what is downstream.

Qt's implementation of the observer pattern is signals and slots. A signal is an event emitted by an object. A slot is a callable that responds to a signal. You connect them with .connect().

Connecting built-in signals

from PySide6.QtWidgets import QApplication, QWidget, QVBoxLayout, QSlider, QLabel
from PySide6.QtCore import Qt

app = QApplication([])
win = QWidget()
layout = QVBoxLayout(win)

slider = QSlider(Qt.Orientation.Horizontal)
slider.setRange(0, 100)
slider.setValue(50)

label = QLabel("Value: 50")

# ── Connect a signal to a slot ────────────────────────────────────────────────
# QSlider.valueChanged(int) is emitted every time the slider moves.
# We connect it to a lambda that updates the label text.
# The int argument from the signal is automatically passed to the lambda.
slider.valueChanged.connect(lambda v: label.setText(f"Value: {v}"))

layout.addWidget(slider)
layout.addWidget(label)
win.show()
app.exec()

Custom signals on a QObject subclass

You can define your own signals on any class that inherits QObject. Custom signals are declared as class-level Signal instances with the argument type(s) they carry. This is how the timeline widget in Demo 2 notifies the rest of the application when the current frame changes:

from PySide6.QtCore import QObject, Signal

class TimelineWidget(QObject):
    """A reusable animation timeline component.

    Signals:
        frame_changed: Emitted whenever the current frame advances.
                       Carries the new frame number as an int.
    """

    # Declare the signal at class level.
    # Signal(int) means this signal carries one integer argument.
    frame_changed = Signal(int)

    def _advance_frame(self) -> None:
        """Called by QTimer on every tick. Advances the frame counter."""
        self._current_frame += 1
        if self._current_frame >= self._total_frames:
            self._current_frame = 0

        # Emit the signal. All connected slots receive the new frame number.
        # The timeline does NOT need to know what is connected to it.
        self.frame_changed.emit(self._current_frame)

# ── Connecting the custom signal ─────────────────────────────────────────────
timeline = TimelineWidget()
viewport = GLViewport()

# Connect: whenever the frame changes, tell the viewport to update.
timeline.frame_changed.connect(viewport.set_frame)

# Connect the same signal to multiple slots — they all fire in connection order.
timeline.frame_changed.connect(curve_editor.set_playhead)
timeline.frame_changed.connect(status_bar.update_frame_display)

Disconnecting and Lambda slots

# Lambda slots for simple one-liners:
btn.clicked.connect(lambda: label.setText("Clicked!"))

# Store the lambda if you need to disconnect it later.
# You cannot disconnect an anonymous lambda — Python creates a new object
# every time you write lambda, so the identity check fails.
handler = lambda: label.setText("Clicked!")
btn.clicked.connect(handler)
# ... later ...
btn.clicked.disconnect(handler)   # works because handler is the same object

Animation rigs are signal graphs: In Maya, when you connect an attribute from one node to another (Node A.output → Node B.input), Maya creates an internal dependency graph edge — exactly the same observer pattern. Moving a rig control fires a cascade of updates through the dependency graph: the IK solver slot fires, the skin deformer slot fires, the blend shape driver slot fires. PySide6 signals and slots are a simpler version of the same mechanism. Understanding one helps you understand the other.

5. The Animation Loop in Qt

QTimer: the Qt way to drive a repeating callback

QTimer fires a timeout signal at a fixed interval. It is the Qt equivalent of setInterval() in JavaScript — but because it integrates with Qt's event loop, it is safe to update widgets directly from the connected slot, with no locks or thread marshalling required.

from PySide6.QtCore import QTimer

# FPS constant — the target frame rate for the animation loop.
TARGET_FPS: int = 60

# Interval in milliseconds between timer ticks.
# Integer division: 1000 // 60 = 16 ms per frame (~62.5 Hz).
TIMER_INTERVAL_MS: int = 1000 // TARGET_FPS

timer = QTimer()
timer.setInterval(TIMER_INTERVAL_MS)

# Connect the timeout signal to the update function.
# This slot runs in the main thread, so it is safe to call widget.update().
timer.timeout.connect(self._on_tick)

timer.start()   # begin firing

# Stop the loop — safe to call even if the timer is already stopped.
timer.stop()

QElapsedTimer: accurate delta time

QTimer fires approximately on schedule, but Qt's event loop may be busy when the timeout falls due — the callback fires slightly late. For frame-rate-independent animation, always measure the actual elapsed time with QElapsedTimer rather than assuming a fixed delta:

from PySide6.QtCore import QElapsedTimer

# ANIMATION CONCEPT: delta time.
# Never animate by a fixed amount per tick.
# Always multiply your velocity by the elapsed time in seconds.
# This gives the same result at 30fps, 60fps, and 120fps.

elapsed_timer = QElapsedTimer()
elapsed_timer.start()

def _on_tick(self) -> None:
    """Timer slot — called every frame."""
    # elapsed() returns milliseconds since start() or restart().
    elapsed_ms: int = self._elapsed_timer.restart()  # also resets to 0

    # Convert to seconds for animation math.
    delta: float = elapsed_ms / 1000.0

    # Update animation state using delta time.
    # rotation_speed is in radians per second.
    self._angle += self._rotation_speed * delta   # frame-rate independent
    self.update()   # schedule a repaint (does not paint immediately)

The update cycle

Calling widget.update() does not paint immediately — it schedules a repaint request. Qt coalesces multiple update() calls within one event loop iteration into a single repaint, preventing redundant work. The actual painting happens when Qt processes the repaint event and calls paintEvent() (for QWidget) or paintGL() (for QOpenGLWidget).

QTimer precision: QTimer is not a high-precision timer. It fires when Qt's event loop processes the timeout event, which may be several milliseconds later than requested. At 60fps with a 16ms interval this drift is negligible for animation. For accurate timing — music sync, physics simulation — use QElapsedTimer to measure actual elapsed time, never accumulate fixed deltas. This is the same reason Three.js uses THREE.Clock.getDelta() rather than assuming a fixed 16ms per frame.

6. Custom Painting with QPainter

The QPainter model

QPainter is Qt's 2D drawing API. You use it inside a paintEvent() override on a QWidget subclass. The coordinate system has its origin at the top-left corner, with Y increasing downward — the same as the HTML Canvas 2D API that Chapter 01 used to draw the easing curve display.

QPainter is a painter in the classic sense: you set a pen (stroke), set a brush (fill), then issue drawing commands. The state machine carries those settings until you change them.

from PySide6.QtWidgets import QWidget
from PySide6.QtGui import QPainter, QPen, QBrush, QColor, QPainterPath
from PySide6.QtCore import Qt

class CurveCanvas(QWidget):
    """A custom QWidget that draws an animation curve with QPainter."""

    def paintEvent(self, event) -> None:
        """Qt calls this whenever the widget needs to be redrawn.

        Never call this method directly — call self.update() to schedule
        a repaint, and Qt will call paintEvent at the right time.
        """
        painter = QPainter(self)

        # Antialiasing: smooth diagonal lines and curves.
        # Same concept as WebGL's MSAA or canvas 2D's imageSmoothingEnabled.
        painter.setRenderHint(QPainter.RenderHint.Antialiasing)

        w, h = self.width(), self.height()

        # ── Draw background ──────────────────────────────────────────────────
        painter.fillRect(0, 0, w, h, QColor("#161a22"))

        # ── Set pen: stroke color and width ─────────────────────────────────
        pen = QPen(QColor("#4f9cf9"), 2.0)   # blue, 2px
        pen.setStyle(Qt.PenStyle.SolidLine)
        painter.setPen(pen)

        # ── Draw grid lines ──────────────────────────────────────────────────
        grid_pen = QPen(QColor("#252b38"), 1.0)
        grid_pen.setStyle(Qt.PenStyle.DashLine)
        painter.setPen(grid_pen)
        for i in range(1, 4):
            y = int(h * i / 4)
            painter.drawLine(0, y, w, y)   # horizontal grid lines

        # ── Draw a Bézier curve with QPainterPath ────────────────────────────
        painter.setPen(QPen(QColor("#4f9cf9"), 2.5))
        painter.setBrush(Qt.BrushStyle.NoBrush)   # no fill inside the path

        path = QPainterPath()
        path.moveTo(0, h)                          # start at bottom-left
        # cubicTo(c1x, c1y, c2x, c2y, endX, endY)
        # Control points define the tangents at start and end.
        # This is the same cubic Bézier as CSS cubic-bezier() and Three.js.
        path.cubicTo(
            w * self._p1x, h * (1 - self._p1y),  # control point 1
            w * self._p2x, h * (1 - self._p2y),  # control point 2
            w, 0                                   # end at top-right
        )
        painter.drawPath(path)

        # ── Draw handle dots ─────────────────────────────────────────────────
        painter.setPen(QPen(QColor("#a78bfa"), 1.5))
        painter.setBrush(QBrush(QColor("#a78bfa")))
        r = 5   # handle radius in pixels
        painter.drawEllipse(int(w * self._p1x) - r, int(h * (1 - self._p1y)) - r, r*2, r*2)
        painter.drawEllipse(int(w * self._p2x) - r, int(h * (1 - self._p2y)) - r, r*2, r*2)

        painter.end()   # explicitly end the painter — good practice in paintEvent

Transforms: translate, rotate, scale

# Transforms in QPainter work like the HTML Canvas 2D API:
# they affect all subsequent drawing commands.

# save() pushes the current transform and pen/brush state onto a stack.
# restore() pops it back — same as canvas.save() / canvas.restore().
painter.save()

painter.translate(cx, cy)           # move the origin to (cx, cy)
painter.rotate(angle_degrees)       # rotate around the new origin
painter.scale(sx, sy)               # scale around the new origin

painter.drawRect(-50, -50, 100, 100)  # draws centred on (cx, cy), rotated

painter.restore()   # undo all transforms — back to the saved state

The cubic Bézier algorithm

The Bézier easing curve displayed by Demo 3 uses the same cubic Bézier polynomial that appears in CSS transition-timing-function: cubic-bezier(), in Chapter 01's easing demos, and in Three.js's InterpolateSmooth. The parametric form gives XY position as a function of curve parameter u ∈ [0, 1]:

import numpy as np

def cubic_bezier_point(u: float, p0: float, p1: float, p2: float, p3: float) -> float:
    """Evaluate a cubic Bézier polynomial at parameter u.

    The standard Bernstein form: sum of basis polynomials weighted by control points.
    This is the same formula used in CSS cubic-bezier() and Three.js CatmullRom easing.

    Args:
        u: Curve parameter in [0, 1].
        p0, p1, p2, p3: Control point ordinates (X or Y, not both at once).

    Returns:
        The interpolated value at u.
    """
    # Precompute 1-u for clarity and efficiency.
    v = 1.0 - u
    # Bernstein basis polynomials B_{i,3}(u):
    # B_{0,3} = (1-u)^3,  B_{1,3} = 3u(1-u)^2,  B_{2,3} = 3u^2(1-u),  B_{3,3} = u^3
    return (v**3) * p0 + 3 * (v**2) * u * p1 + 3 * v * (u**2) * p2 + (u**3) * p3

The challenge: the CSS cubic-bezier() function gives time t as input and eased value as output, but the parametric form gives both as functions of u. To find the eased value for a given t, we must invert the X component — find the u where bezier_x(u) = t — using a binary search. This is the same inversion that browsers perform internally for every CSS transition.

QPainter ≈ HTML Canvas 2D: If you used ctx.bezierCurveTo() in Chapter 01's easing display, QPainter's path.cubicTo() is the identical operation. Both APIs share the same painter's model: pen, fill, path, transforms, save/restore. The coordinates are mirrored (Canvas: Y down; same for QPainter), and the curve math is the same cubic Bézier. Code you understand in one context transfers directly to the other.

7. OpenGL in Python: PyOpenGL + QOpenGLWidget

Why embed OpenGL in Qt?

Every professional DCC tool has a real-time 3D viewport: Maya's perspective view, Nuke's viewer, Houdini's scene view. All of these are OpenGL contexts embedded inside Qt windows. QOpenGLWidget is exactly the class they use. Learning to embed OpenGL in Qt is learning the architecture of the viewport in every tool you will use professionally.

The GPU pipeline inside paintGL() is identical to what you wrote in Chapter 01 with raw WebGL: the same VAO/VBO/EBO model, the same vertex and fragment shaders, the same MVP matrix, the same depth test. The difference is the language (Python instead of JavaScript) and the API prefix (GL.gl* instead of gl.*).

PyOpenGL and PyOpenGL_accelerate

PyOpenGL provides Python bindings for the full OpenGL API — every function in the C API is available as a Python call in the OpenGL.GL namespace. PyOpenGL_accelerate is a companion C extension that replaces Python-level type conversions (buffer pointer checks, array validation) with fast C code, giving a 2–10× speedup on buffer uploads and uniform setting. Always install both:

uv sync   # installs both, as declared in pyproject.toml

Always import as from OpenGL import GL and use the GL. prefix. Never use from OpenGL.GL import * — star imports hide where functions come from, break linting, and make it impossible to grep for where a specific GL call is made.

QSurfaceFormat: requesting the right OpenGL version

Before creating a QApplication, you must tell Qt which OpenGL version and profile you need. This is done with QSurfaceFormat. If you skip this, Qt may give you a legacy OpenGL 2.1 context — which lacks VAOs, core shaders, and everything else from Chapter 01.

import sys
from PySide6.QtWidgets import QApplication
from PySide6.QtGui import QSurfaceFormat

# CRITICAL: set the surface format BEFORE creating QApplication.
# This tells Qt which OpenGL version to request from the OS.
fmt = QSurfaceFormat()
fmt.setVersion(3, 3)          # Request OpenGL 3.3 — same as WebGL 2's feature set

# Core profile: removes all deprecated legacy OpenGL functions.
# This is the correct professional setting. It mirrors WebGL 2's behaviour.
fmt.setProfile(QSurfaceFormat.OpenGLContextProfile.CoreProfile)

fmt.setDepthBufferSize(24)    # 24-bit depth buffer (standard)
fmt.setSamples(4)             # 4x MSAA antialiasing

# Apply globally — all QOpenGLWidgets created after this use this format.
QSurfaceFormat.setDefaultFormat(fmt)

app = QApplication(sys.argv)  # QApplication MUST come after setDefaultFormat

QOpenGLWidget: three methods to override

from PySide6.QtOpenGLWidgets import QOpenGLWidget
from OpenGL import GL

class CubeViewport(QOpenGLWidget):
    """An OpenGL viewport embedded inside a Qt window.

    Override these three methods. Never call OpenGL functions outside them —
    the OpenGL context is only guaranteed to be current inside these methods.
    """

    def initializeGL(self) -> None:
        """Called once when the OpenGL context is first created.

        This is the correct place for ALL one-time GL setup:
        compile shaders, create VAOs/VBOs, upload static geometry.
        The context is current here — GL calls are safe.
        """
        # Enable depth testing — same as gl.enable(gl.DEPTH_TEST) in WebGL.
        GL.glEnable(GL.GL_DEPTH_TEST)

        # Enable MSAA if the surface format requested samples > 1.
        GL.glEnable(GL.GL_MULTISAMPLE)

        self._setup_shaders()   # compile and link GLSL programs
        self._setup_geometry()  # create VAO, VBO, EBO, upload vertex data

    def resizeGL(self, w: int, h: int) -> None:
        """Called every time the widget is resized.

        Update the OpenGL viewport and recompute the projection matrix.
        w, h are the new widget dimensions in physical pixels.
        """
        # glViewport: tell OpenGL which part of the window to draw into.
        # Same as gl.viewport(0, 0, canvas.width, canvas.height) in WebGL.
        GL.glViewport(0, 0, w, h)

        # Recompute projection with the new aspect ratio.
        aspect = w / max(h, 1)
        self._proj_matrix = mat4_perspective(
            fovy=60.0, aspect=aspect, near=0.1, far=100.0
        )

    def paintGL(self) -> None:
        """Called every frame to draw the scene.

        Triggered by self.update() (from QTimer or user interaction).
        The context is current here — all GL draw calls are safe.
        """
        GL.glClearColor(0.05, 0.06, 0.08, 1.0)
        GL.glClear(GL.GL_COLOR_BUFFER_BIT | GL.GL_DEPTH_BUFFER_BIT)

        # Update rotation using delta time — frame-rate independent.
        delta = self._elapsed_timer.restart() / 1000.0
        self._angle_y += self._speed_y * delta   # radians per second

        # Build the model matrix (rotation) and upload MVP to the shader.
        model = mat4_rotate_y(self._angle_y)
        self._upload_uniforms(model, self._view_matrix, self._proj_matrix)

        GL.glBindVertexArray(self._vao)
        GL.glDrawElements(GL.GL_TRIANGLES, 36, GL.GL_UNSIGNED_INT, None)
        GL.glBindVertexArray(0)

Note on matrix transpose: WebGL's uniformMatrix4fv(loc, false, matrix) — the false means "do not transpose; the matrix is already column-major." PyOpenGL's glUniformMatrix4fv(loc, 1, GL_TRUE, matrix) — the GL_TRUE means "transpose before uploading." This difference arises because NumPy arrays are row-major by default, but OpenGL expects column-major matrices. By passing GL_TRUE, we tell OpenGL to transpose on upload, which corrects for NumPy's layout.

NumPy for vertex data and matrix math

import numpy as np

# ALWAYS use dtype=np.float32 for vertex data.
# OpenGL expects 32-bit IEEE 754 floats; Python floats are 64-bit.
# Passing a 64-bit array will silently upload garbage or crash.
vertices = np.array([
    # x      y      z      r     g     b
    -0.5,  -0.5,   0.5,   1.0,  0.0,  0.0,   # front-bottom-left (red)
     0.5,  -0.5,   0.5,   0.0,  1.0,  0.0,   # front-bottom-right (green)
     0.5,   0.5,   0.5,   0.0,  0.0,  1.0,   # front-top-right (blue)
    # ... 5 more faces ...
], dtype=np.float32)

# ALWAYS use dtype=np.uint32 for index data.
indices = np.array([0, 1, 2, 2, 3, 0, ...], dtype=np.uint32)

# Upload: data.nbytes is the size in bytes, not the number of elements.
GL.glBufferData(GL.GL_ARRAY_BUFFER, vertices.nbytes, vertices, GL.GL_STATIC_DRAW)

# ── Matrix math with NumPy ────────────────────────────────────────────────────
# Note: in production, use glm (PyGLM) or pyrr for convenience.
# Here we build matrices manually so you see the math.

def mat4_perspective(fovy: float, aspect: float, near: float, far: float) -> np.ndarray:
    """Build an OpenGL perspective projection matrix.

    Equivalent to THREE.PerspectiveCamera(fovy, aspect, near, far) and
    mat4.perspective() from gl-matrix in Chapter 01.
    """
    f = 1.0 / np.tan(np.radians(fovy) / 2.0)
    return np.array([
        [f / aspect, 0,  0,                              0],
        [0,          f,  0,                              0],
        [0,          0,  (far + near) / (near - far),   -1],
        [0,          0,  (2 * far * near) / (near - far), 0],
    ], dtype=np.float32)

8. Composing a Desktop Animation Tool

MVC architecture for animation applications

A professional animation application separates its concerns into three layers — the classic Model-View-Controller (MVC) pattern:

  • Model — pure animation data and math. No Qt imports. A Python dataclass or plain object that holds the current frame, keyframe values, easing parameters, and an evaluate(frame) method. Because the model has no Qt dependency, it can be unit-tested, serialised to disk, and reused in a non-GUI context (e.g. a render farm script that uses the same curve math).
  • View — Qt widgets. The OpenGL viewport, the timeline scrubber, the curve editor, the parameter panel. Views read from the model but never modify it directly — they emit signals when the user changes something.
  • Controller — the MainWindow or a separate controller object. Connects View signals to Model updates and triggers View refreshes. It is the glue: "when the timeline emits frame_changed(42), call model.current_frame = 42, then call viewport.update()."

Why separate the model from Qt? Blender, Maya, and Nuke all follow this principle. The animation curve data in Maya's Graph Editor is a pure C++ data structure (the MFnAnimCurve) — no UI code touches it. The UI (the Graph Editor widget) reads from it, and the controller (Maya's undo/redo system) modifies it. Keeping the model Qt-free means it can run on a render farm, be serialised to USD, or be called from a unit test — the same data layer works everywhere.

QSplitter: resizable panel layouts

QSplitter divides a space between two or more widgets with a draggable handle. It is how every DCC tool implements its multi-panel layout.

from PySide6.QtWidgets import QSplitter

Signal flow in Demo 5

The mini animation tool (Demo 5) connects four panels exclusively through signals — no panel calls methods on another panel directly. This is the correct professional architecture:

TimelineWidget.frame_changed(int)
    → MainWindow._on_frame_changed(frame)
        → BounceAnimation.current_frame = frame      # update model
        → GLViewport.set_frame(frame)                # update 3D view
        → CurveEditor.set_playhead(frame)            # update curve playhead
        → statusBar().showMessage(...)               # update status text

ParameterPanel.bounce_height_changed(float)
    → BounceAnimation.bounce_height = value          # update model
    → CurveEditor.update()                           # redraw curve
    → GLViewport.update()                            # re-render

CurveEditor.easing_changed(float, float)             # emitted when handles dragged
    → BounceAnimation.easing_p1 = value              # update model
    → BounceAnimation.easing_p2 = value
    → GLViewport.update()                            # re-render with new easing

Each panel owns its own display logic. No panel imports another panel's class. The MainWindow is the only place that knows about all four panels — it creates them and connects their signals. This is clean, testable, and scalable: adding a fifth panel only requires wiring it up in MainWindow.
